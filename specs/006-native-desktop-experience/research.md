# Research: A Native Desktop Experience

## R1 — What exists today (checked in the code)

- **Window** (`apps/desktop/src/main/window.ts`): one `BrowserWindow`, OS frame, `backgroundColor: '#ffffff'`, `show: false` until `ready-to-show`, sandbox, context isolation, saved bounds and maximised state. No `nativeTheme`, `powerMonitor`, `Tray`, badge, accelerators, login item, protocol or file handlers, `titleBarStyle` or material anywhere in `apps/desktop/src`.
- **Menu** (`menu.ts`): File/Edit/View/Window/Help mostly made of roles, three Help links, labels from `menu-labels.ts` (en/uk/pl).
- **Bridge**: `about`, `revealDataFolder`, `setLanguage` and the `updates` group, one frozen global, strict zod schemas on both sides, fixed channels, sender check in `ipc.ts`.
- **Lock** (`packages/core/src/identity/application/lock.ts`, used by the Core Worker): the session is `unlocked` or `locked`. Locking wipes the keys, closes the database and **terminates the worker**. `covered()` is true when locked, when the page is hidden, or when the window is out of focus. A hidden page starts a timer that locks after `hiddenGraceMs` (default **1 minute**); inactivity locks after `idleMs` (default **5 minutes**). `pageHide` locks at once.
- **Page side** (`CoreProvider.tsx`): `covered = hidden || blurred`; it forwards `visibilitychange`, `blur`, `focus` and `pagehide` to the worker.
- **Reminders**: shown by a component inside the Schedules view (`SchedulesView.tsx` `Reminders`), checked every 60 s, **only while that view is on screen**, for the selected Fold, using the web `Notification`. The desktop permission handler grants only `persistent-storage` and `publickey-credentials-get`, so notifications are denied in the desktop app today.
- **Waiting count**: `useScheduleInbox` (selected Fold, the `schedules.pending` query).
- **Files**: backups are `<name>.cashfold-backup`; CSV import accepts at most `MAX_IMPORT_ROWS = 20,000` rows; attachments at most `MAX_ATTACHMENT_MB = 25`.
- **Theme**: stored in the page's own `cashfold.ui` preferences; `THEME_BOOTSTRAP` applies it before first paint; token backgrounds are `#ffffff` (light) and `#09090b` (dark).
- **Single instance**: the shell already requests the lock and handles `second-instance`.

Three consequences shape the design: reminders and the badge need a shell-level service in the page (they cannot rely on the Schedules view); the 1-minute hidden-window lock would defeat background reminders; and notification permission must be granted for the app origin.

## R2 — Decisions

**D1. Lock policy on desktop (area 1).**
Decision: the shell reports `lock-screen` (macOS, Windows), `suspend` (all), and a 5 s poll of `powerMonitor.getSystemIdleState` that reports `locked` (macOS, Windows, covers screen saver and fast user switching where the system exposes it) as one typed event `systemLock` with a reason. The page answers by locking exactly as the "Lock" button does. Rationale: the page owns the session, the shell stays free of keys and data. In `CoreProvider`, on desktop: blur no longer covers or tells the worker unless `hideOnBlur` is on. Alternatives: lock inside the shell (rejected: it cannot reach the worker's keys, and a second lock path would diverge); hide on blur by default (rejected by the spec).
Linux: `suspend` and the idle timer are what is promised. Screen-lock on GNOME/KDE goes through D-Bus signals that Electron does not expose; adding a D-Bus library for it is not worth a new dependency (principle IX), so FR-005 applies: Settings says what the system can report (`capabilities`).

**D1b. A hidden window must not lock after one minute on desktop.**
Decision: on desktop the page no longer forwards "hidden" to the worker's hidden-window timer; the window can still be covered visually while hidden, but the lock then comes from `idleMs` (the person's idle time) and from the system events above. Rationale: with the default `hiddenGraceMs` of one minute, an app kept in the tray would lock after a minute and reminders would never fire, which defeats area 5 and the spec's own assumption ("until the idle time locks it"). The change moves a hidden window from "locks after 1 minute" to "locks after the idle time (default 5 minutes)", offset by the new system-lock events. Alternative: raise the default `hiddenGraceMs` (rejected: it would change the web app too). This goes in the threat-model note and ADR-0012.

**D2. First frame colours (area 2).**
Decision: the page tells the shell its theme choice whenever it changes (`setTheme`); the shell mirrors it in its state file, sets `nativeTheme.themeSource` to it at launch, and creates the window with the matching `backgroundColor` (`#ffffff` / `#09090b`, kept equal to the tokens by a test). With "System", the shell follows `nativeTheme` and the window colour is updated on `updated`. On the very first launch the source is "system". If the page's stored theme and the mirror ever disagree (site data cleared), the page corrects the mirror at start. Setting `themeSource` also makes `prefers-color-scheme` agree with the person's choice. Alternatives: reading the page's local storage from the shell (rejected: not reachable before the page loads, and sandboxing forbids it).

**D3. Menus and shortcuts (area 3).**
Decision: one typed action model (`new-transaction`, `lock`, `settings`, `search`, `go:overview|transactions|accounts|plan|settings`, `import`, `export`) produces both the menu items and the accelerators; choosing one sends `menuAction` to the page, which maps it to the router and sheets. Accelerators in [contracts/menu-and-shortcuts.md](contracts/menu-and-shortcuts.md). While locked, the page reports `session: locked`, the shell disables the data actions and the page shows the unlock screen if one is triggered. Menu text comes from `menu-labels.ts`, extended for en/uk/pl; the menu is rebuilt on language, session and settings changes. Alternatives: handling shortcuts only in the page (rejected: the menu must show working shortcuts, and menu accelerators work even when focus is in a field).

**D4. Context menus (area 4).**
Decision: a native pop-up (`Menu.popup`) requested through one bridge call that carries a validated list (at most 12 items, ids matching `^[a-z][a-z-]{0,23}$`, labels at most 60 characters, an optional `destructive` flag). The shell answers with the chosen id or none. The rows' existing action definitions are lifted into one function per row type that serves both the actions button and the context menu, so the two cannot differ (FR-012). Delete keeps its confirmation dialog. The context-menu key and Shift+F10 raise the same `contextmenu` event. Alternative: a menu drawn by the page (rejected: not native, and it repeats focus handling).

**D5. Dropping files (area 4).**
Decision: standard drag events in the page, only when running in the desktop app. The page cancels the default (otherwise the window would try to navigate to the file; navigation is also blocked by `will-navigate`), checks the kind (extension and type) and size, and hands the `File` to the import panel through a small in-memory hand-off, or to the add sheet's attachment field. Nothing is read until the person confirms. While locked, a drop is ignored with a message. Limits: CSV 16 MiB (the 20,000-row cap in `core` is the real bound), attachments 25 MB as today. Alternative: shell-side drop handling by path (rejected: the shell would read files on the page's say-so, with no gain).

**D6. Badge (area 5).**
Decision: the page's `ReminderService` computes the waiting count for the selected Fold and calls `setBadge(n)` (0 to 999). macOS and Linux (where supported) use `app.setBadgeCount`. Windows has no count API: the shell shows an overlay icon from nine pre-rendered number images and "9+", generated by the brand-asset script, with an accessible description. The page sends 0 on lock; the shell also clears the badge itself on `systemLock` and on quit, so a stuck renderer cannot leave a count behind (clarification 1). **Scope for this release: the currently selected Fold** (the existing `schedules.pending` query is per Fold); counting across all Folds would need a per-Fold query for each and is a follow-up. Alternative: keep the count in a file so it survives a lock (rejected: that is exactly the plaintext metadata clarification 1 refused).

**D7. Reminders and notifications (area 5).**
Decision: move reminders out of `SchedulesView` into a `ReminderService` mounted once in the unlocked shell, running whatever screen is open, using the existing `showDueReminders`, the existing 60 s check and the existing "show amounts" opt-in. The desktop permission handler additionally grants `notifications` for the app origin; the page's `Notification` is shown natively by the system. Choosing one calls `showWindow()` and navigates. After an unlock, if more than one reminder fell due meanwhile, one summary notification is shown instead of many (new text `schedules.notify.message.many`); one reminder is shown as it is today. `backgroundThrottling` is turned off for the main window so a hidden window still fires its 60 s check on time. Locked: the service is gone with the session and nothing is shown. The reminders also run in a browser tab, because the code is shared; this is the one intended change in web behaviour and has a web test. The service worker path in `show()` falls back to `new Notification` if it throws, which is how the desktop app has to work; a test covers it. Alternative: send notifications from the shell (rejected: the shell would need the schedule, which means reading the ledger).

**D8. Tray, menu-bar item, dock menu, jump list (area 5).**
Decision: one `Tray` (template image on macOS; coloured image on Windows and Linux; assets generated from the master mark) with Show Cashfold, Add transaction, Lock, Quit. macOS dock menu (`app.dock.setMenu`) and Windows jump list (`app.setJumpList`): tasks for Add transaction and Lock, launched through arguments that the single-instance hand-over maps to the same action enum; "recent Folds" are added while unlocked from a list the page pushes (names only), and **cleared on every lock, on a system lock and on quit, and the dock menu and jump list are reset to tasks only at every start** (the Windows jump list outlives the process, so a crash must not leave names behind), so the shell's surfaces never show names the locked app hides (FR-020). Linux: the tray exists where the desktop supports status icons; "keep running" is only offered where it is safe (D9). Alternative: recent Folds always shown (rejected by FR-020).

**D9. Background, close behaviour, start at login (areas 5 and 6).**
Decision (staged: the mechanism is built in the foundation but inactive, so closing behaves as today; step 5 activates it with the tray item and its Settings switch, step 6 adds start at login): "keep running" means closing **hides** the window (the page, its timers and the unlocked session stay alive until locked), with `before-quit` setting a flag so Quit really quits. Defaults: quit on Windows and Linux, keep running on macOS. On Linux "keep running" is offered only when `XDG_CURRENT_DESKTOP` names a desktop known to show status icons (KDE, XFCE, Cinnamon, MATE, LXQt, Budgie, Pantheon, Deepin); on plain GNOME it is not offered, because without an extension there is no way to bring the app back (FR-021, FR-023). Start at login: `app.setLoginItemSettings` on Windows and macOS with a hidden-start argument; on Linux an autostart `.desktop` entry written by the shell (Electron has no API there) pointing at the AppImage path or the installed executable. The app then starts without showing a window and, having no session, is locked by definition. Alternatives: always keep running (rejected: unexpected on Windows and Linux), a separate background helper process (rejected: more code and a second thing to secure).

**D10. Opening files and links (area 6).**
Decision: the shell parses everything in `intake.ts` with the strict grammar in [contracts/link-and-file-intake.md](contracts/link-and-file-intake.md). Sources: macOS `open-file` and `open-url` (queued if they arrive before `ready`); Windows and Linux command-line arguments, including those of a second launch (`second-instance`). Files are opened by the shell with a descriptor, checked as regular files and size-limited before reading; links must match the grammar and must not contain secrets (clarification 2). **The shell holds intake items until the page reports `unlocked` and only then delivers them**, so a locked renderer never holds file contents (FR-015). The page shows each item for review on the matching screen (import preview, restore form, add-device form with the email and service address filled and the Secret Key empty). Several items are queued and shown one at a time. Packaging: the `cashfold` scheme and the `.cashfold-backup` extension are registered; CSV is registered as an alternative handler only, so Cashfold never becomes the default CSV program (the spec says "once chosen").

**D11. The frame (area 7).**
Decision: macOS `titleBarStyle: 'hidden'` with the traffic lights positioned inside the top bar; Windows `titleBarStyle: 'hidden'` with `titleBarOverlay` (colour and symbol colour updated on theme change; height equal to the top bar); Linux keeps the system frame. The page marks `<html>` with `data-frame` and `data-platform` from a synchronous `platform` string on the bridge, so layout is right on the first paint; the top bar is a drag region with every control `no-drag`; left inset for the traffic lights (cleared in full screen, reported by a `frameState` event) and right inset from `env(titlebar-area-*)` on Windows. Double-click maximise and snapping are the system's behaviour for drag regions. Translucency: macOS `vibrancy: 'sidebar'`, Windows 11 `backgroundMaterial: 'mica'` (build 22621 or later); the sidebar background becomes transparent only when `data-translucent` is set, which the page does when the shell reports it is active; `nativeTheme.prefersReducedTransparency` or `shouldUseHighContrastColors` turns it off live. Alternatives: a fully custom title bar on Linux (rejected: wrong on many desktops), drawing our own window buttons on Windows (rejected: loses snap layouts).

**D12. Settings and where they live.**
Decision: desktop preferences (`hideOnBlur`, `startAtLogin`, `closeBehavior`, and the theme mirror) live in the shell's state file, read and changed through `settings`/`setSettings` on the bridge and shown in a new Settings → Desktop section that exists only in the desktop app. The idle time stays where it is (Settings → Profile and security → locking) with a note that it also governs a hidden window (D1b). Alternative: store in the web preferences (rejected: the shell must read start-at-login and close behaviour before any page exists).

**D13. Testing.** Test hooks exist only when the build defines `__CASHFOLD_TEST_HOOKS__`, a compile-time constant set by `apps/desktop/scripts/build.mjs` like the existing test-feed define; a release bundle is checked to contain none of them.

Shell logic in Vitest with the Electron objects behind small interfaces (as `ipc.ts` and `menu.ts` already do). Packaged-app Playwright specs per area: menu actions through `electronApp.evaluate` clicking menu items, `powerMonitor.emit('lock-screen')` and `('suspend')` in the test build, `app.getBadgeCount()`, tray and jump-list objects, `second-instance` with arguments, drops through dispatched `DragEvent`s with a `DataTransfer`, theme by setting `nativeTheme.themeSource`. A test pins the window colours to the tokens. The web suite proves nothing changed in a browser.

**D14. Documentation and process.**
A threat-model section and ADR-0012 (the lock policy and hidden-window change, and the intake rules); `docs/desktop.md` updated; both lock (P1) and intake (P6) pull requests marked for two reviewers as the constitution requires for security-sensitive changes.

## Spec adjustments (applied on 2026-10-25 after the analysis)

1. FR-003 and Settings text: say that, on desktop, the idle time also governs a window kept hidden or minimised (D1b).
2. FR-016: say that the badge and reminders cover the **selected Fold** in this release.
3. Key Entities: add that "Desktop preferences" live in the shell's state file, not the web preferences.
