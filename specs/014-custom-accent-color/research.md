# Research: Custom Primary Color

## R1 Palette, not a free picker
- **Decision**: About ten named colors (default emerald, then e.g. blue, indigo, violet, pink, red-orange, amber, teal, slate), each with hand-set light and dark token values.
- **Rationale**: Contrast (FR-004, SC-003) and icon quality can be tested for every option; a free picker needs runtime contrast math and runtime icon drawing.
- **Alternatives**: free color picker with derived tokens (more code, unpredictable contrast, no pre-rendered icons).

## R2 How the color is applied
- **Decision**: A `data-primary` attribute on `<html>` next to `data-theme`; `tokens.css` overrides `--primary`, `--on-primary`, `--accent-text` and `--focus` per color and theme. Components already use these tokens, so nothing else changes.
- **Rationale**: Same mechanism as the theme, no re-render, works before first paint.
- **Alternatives**: setting CSS variables from JS (needs inline values per theme change, harder to test, flashes).
- **Check**: grep for hard-coded emerald/green classes that bypass the tokens; replace with tokens (chart accents included). Danger/success/warning tokens are left alone (FR-005).

## R3 No flash at launch
- **Decision**: Extend the inline bootstrap to read `primary` from `cashfold.ui` and set `data-primary`; keep it equivalent to the typed parser (existing equivalence test pattern). The page's CSP hash is regenerated by `harden-html.mjs` automatically.

## R4 Icons per color
- **Browser tab**: swap `<link rel="icon">` to the pre-rendered file for the color.
- **Install**: replace `<link rel="manifest">` with a generated blob manifest pointing at the colored icons. **Verify** against the CSP (`manifest-src`) and that Chrome/Edge accept a blob manifest before relying on it; fall back to the default icons plus the explanatory note (FR-007) if not.
- **Already installed**: the system fixes the icon; the settings show a note (FR-007).
- **Alternatives**: runtime canvas rendering (extra code, cannot beat the system's install-time rule).

## R5 Desktop icon
- **Decision**: New bridge call sends the color id (validated against the palette in the main process); main sets the dock icon (macOS), window icon (Windows/Linux) from the bundled `apps/desktop/build/icons/<color>.png`. The tray uses a macOS template image that stays monochrome; the colored tray image on Windows/Linux follows the color if cheap, else is left default and noted.
- **Rationale**: Sending an id, never an image path or bytes, keeps the bridge narrow. The packaged app icon in the OS launcher/installer cannot change after install; only the running dock/window icon does.

## R6 Where the choice lives
- **Decision**: Add `primary` to the prefs object with a default (no version bump needed, parsing is defensive field by field). Reset in Appearance restores it.

## R7 Syncing across devices (Phase 3)
- **Finding**: `cashfold.ui` prefs are "device-local, never synced or exported". Folds are shared among members, so a Fold setting would expose and bind the choice to one Fold.
- **Decision**: A per-account encrypted profile record, keyed from the personal key set (not a Fold Key), stored by the relay as an opaque blob, last-writer-wins by hybrid logical clock. Needs an ADR, protocol schema, server storage and a hostile-server test.
- **Risk**: this is the largest piece of the feature by far for a cosmetic setting. If it is not worth that cost, drop User Story 3 and keep per-device storage; the spec change is small.
- **Alternatives**: write the field into every Fold the person belongs to (leaks to members, many writes); unencrypted server preference (violates zero-knowledge).

## R8 Accessibility
Swatches are a radio group with text names and a visible selected state that is not color-only; the control works by keyboard and screen reader. Every pair is checked in `palette.test.ts`.
