# ADR-0003: In-house deterministic CBOR profile

- **Status**: accepted
- **Date**: 2026-10-18

## Context

Signatures and AEAD associated data need byte-identical encodings on every device (FR-018). The wire format is CBOR with RFC 8949 section 4.2.1 deterministic rules, no floats, and 64-bit integers that must stay exact (`bigint`). JSON cannot give canonical bytes or exact 64-bit integers.

## Decision

Write a small strict codec in `packages/protocol/src/cbor/` (about 300 lines, no dependencies) instead of adopting a general library.

- **Why not a library**: general CBOR libraries accept floats, tags, indefinite lengths and non-shortest integers on decode, decode integers beyond 2^53 to doubles or optional bignums, and differ in map-key ordering (RFC 7049 length-first vs RFC 8949 bytewise). Retrofitting a strict profile on top means validating every decoded value anyway.
- **Profile**: integers only (decoded as `bigint` always; the encoder accepts safe-integer numbers and `bigint`); text (well-formed UTF-8 only, BOM preserved), byte strings, arrays, maps with integer or text keys sorted bytewise by encoded form, booleans and null. Everything else is rejected with a typed `CborError` code. Nesting depth is capped at 64, and declared lengths are checked against remaining input before any allocation.
- **Verification**: frozen vectors in `vectors/cbor/deterministic.json` (41 valid, 38 invalid), whose valid cases were decoded with the independent `cbor2` library; property tests for round trip, canonical idempotence, insertion-order independence and one-bit mutation; structured fuzzing follows in T033.

## Consequences

The codec is security-relevant code and falls under the two-reviewer rule for protocol parsing changes. Adding a type (for example tags) is a profile change and needs a new ADR plus new vectors.
